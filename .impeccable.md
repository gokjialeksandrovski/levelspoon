# Per100 — Design Context

_Written by `/impeccable teach`, 2026-09-09. Sourced from direct user answers, not inferred from code._

## Users

People logging what they eat, tracked per-100g. Used in short, frequent bursts spread across the day — standing in a kitchen, at a restaurant table, mid-grocery-run — not a sit-down session. Often one-handed, often mid-bite. Opened many times a day, every day, for as long as the habit sticks.

## Brand Personality

**Warm & tactile.** Feels like a food journal someone actually keeps by hand — not a spreadsheet, not a game, not a template.

Anti-references (all explicitly rejected):
- **MyFitnessPal-style spreadsheet** — dense clinical tables, no personality, feels like data entry.
- **Duolingo-style gamification** — streaks, mascots, aggressive rewards; too gamified/juvenile for a food log.
- **Generic AI-slop SaaS** — glassmorphism, purple/gradient accents, rounded cards with icons on top; templated, forgettable.

## Aesthetic Direction

The palette and type system already do real work toward "warm & tactile" and should be treated as settled, not reopened:

- Warm cream surfaces (`--raw-bg: #fdfbf7` light / `#1a1816` dark), spiced accent hues (paprika/amber/plum/matcha), generous 16–24px radii (deliberately *not* called "squircle" — spec language already rejects that word).
- Bricolage Grotesque (display) + Karla (body) — an intentional pairing, not a reflex default.
- `--ease-out-quart` / `--duration-step: 260ms` already exist as the app's one shared motion recipe, used by the day-view/wizard slide transition.

**The actual gap is motion craft, not palette or type.** The current animation vocabulary (slide transition, pulse skeleton, button press-spring, log-success pulse) is functional but thin, and two of three most-visited surfaces — meal detail, first app load — currently have **zero animation at all**. That flatness is what reads as "missing human touch," not the color or font choices.

Theme: light and dark both already implemented and must both stay supported (this is a utility app opened at all hours, not a single-context product).

## Design Principles

1. **Motion explains, it doesn't decorate.** Every animation should read as a real thing happening — a number settling, a segment redistributing, an ingredient leaving a list — never a flourish bolted on afterward.
2. **Warmth through craft, not cuteness.** No mascots, no confetti, no bounce/elastic easing. Warmth comes from unhurried pacing and organic (spring) easing, not from playful ornament.
3. **Extend the existing vocabulary before inventing a new one.** Reuse `--duration-step` / `--ease-out-quart` and the four existing motion/react surfaces as the baseline. New motion should feel like a sibling to the log-success pulse and the slide transition, not a different app.
4. **Silence is a state too.** The zero-animation surfaces (meal detail, first load) aren't neutral — they read as unfinished. Close those gaps before adding more motion to surfaces that already have some.
5. **Respect reduced motion absolutely.** Every new animation must degrade through the app's existing `MotionConfig reducedMotion="user"` / `prefers-reduced-motion` path with no exceptions.

## Motion Rules

_Sourced from `ui-ux-pro-max`'s Animation domain (priority 7), narrowed to what actually applies here. Numeric defaults for any new motion work in this repo — deviate only with a reason, same as the app's existing `--duration-step`/`--ease-out-quart` pair._

- **Timing**: 150–300ms for micro-interactions (row entrance, focus states), up to ~400ms for anything more orchestrated (a settle sequence, a page arrival). Nothing over ~700ms for content someone checks dozens of times a day.
- **Properties**: animate `transform` and `opacity` only. Never `width`/`height`/`padding`/`margin` directly — for anything that changes a block's height (an ingredient row collapsing), transition `grid-template-rows`, not `height`.
- **Easing**: `ease-out` for things entering, `ease-in` for things exiting; reach for spring physics (motion/react `type: "spring"`, stiffness ~300 / damping ~20) over another cubic-bezier for the one moment in a sequence that should read as organic rather than mechanical — not for every moment.
- **Sequencing**: stagger list/group items 30–50ms apart. Exits run faster than entrances (~60–70% of the entrance duration) so removal feels responsive rather than reluctant.
- **Meaning**: every animation expresses a cause → effect. If it can't be described as "X happened, so Y moved," it's decoration, not motion — cut it.
- **Reduced motion**: mandatory fallback for every new animation, not just the orchestrated ones — collapses to the instant final state via the app's existing `reducedMotion="user"` wiring.

## Preview Workflow

Claude Design's canvas is built for static/near-static layout artboards — a poor fit for evaluating *motion*, which is inherently about time. For this project, motion concepts are previewed as **live, replayable HTML/CSS artifacts** (real transitions running in the browser, both themes, a reduced-motion toggle) instead of storyboard frames, then ported directly into the real `motion/react` components once the feel is approved.

## Settled Decisions — do not re-flag in critiques

- **Meal naming is "Meal 1", "Meal 2" (ordinal within the local day).** A time-of-day scheme ("Breakfast"/"Lunch"/"Dinner") was tried on 2026-09-17 and reverted by the owner: several meals in one slot all read "Dinner" and could not be told apart. Do not flag ordinal meal names as app-speak or suggest time-derived names again.
